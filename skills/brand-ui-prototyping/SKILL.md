# Brand UI prototyping

Turn a page scope into a reviewed visual direction and working HTML prototype through repeated concept, render, feedback, and revision cycles. A concept image, Figma frame, or code prototype can be the starting point; move between them as the work reveals new issues. Keep approved brand rules fixed while proposals evolve.

## Establish the brief

- Inventory the requested pages, their purpose, audience, content, calls to action, and important states. For a website concept, always include the homepage in the page map, even when the immediate request focuses on inner pages. Read the project scope and actual homepage copy before choosing a hero layout. Record what is confirmed and what is still a proposal.
- Inspect the project's existing design system and user-provided brand assets. If paths are not given, check for a user-local asset source configured for this project, then inspect its color guide and logo files; never use another project's sources as a default. Treat approved logos, color values, and theme definitions as fixed. Use the supplied files and exact values; do not redraw, recolor, approximate, or replace them with generated versions. If an asset type is unavailable, identify the missing input and keep any affected concept explicitly provisional.
- A screenshot of a brand guide is evidence for its written swatches and pairing rules, not a reusable logo or image asset. Read printed hex values rather than sampling screenshot pixels. Distinguish approved color groupings from a loose palette before offering themes.
- Keep a project-local working record of approved assets and pairings, real copy, page scope, current concept and prototype paths, decisions, feedback, and open questions. Record each iteration's specific change and reason so later passes preserve accepted decisions. Keep private client assets and machine-specific paths outside this shared skill and public repositories.

## Find a visual direction

- For a familiar product category, study comparable live products for relevant patterns. For a novel product, break the page into jobs such as orientation, explanation, proof, and action; find a reference for each job, then compose a coherent flow. Record source links and the specific pattern borrowed. Do not copy a full page or mistake a reference's branding for the project's branding.
- When exploring frontend components or visual directions, use https://designeer.xyz/llms-full.txt to find candidates, then check each candidate's official documentation and fit with the existing design system.
- Generate or edit images to explore layout, atmosphere, and illustration ideas when a static visual will clarify the choice. Use an approved logo file in the composition rather than asking an image model to recreate it. Carry approved colors through the exploration, and label generated images as concepts rather than brand source files. Compare viable directions against content length, clarity, and brand fit before selecting one.
- Give the homepage hero one punchy, specific headline that says what the project offers or enables, followed by one short line that clarifies the audience, outcome, or differentiator. Derive both from the confirmed scope; avoid generic slogans or invented claims. Move supporting detail into the next section instead of lengthening the hero. Test whether a first-time visitor can explain the offer after a quick look.
- Decide how many hero calls to action the scope actually needs. Give the main user task one clear primary CTA with an outcome-specific label. Add a visually quieter secondary CTA only when a distinct user path is needed; put additional paths in navigation or later sections. Record the action and destination for each CTA.
- Choose a centered or split (left copy, right visual) hero from the copy, CTA paths, and available assets. A centered layout suits a concise message that benefits from a shared background. A split layout suits a product, workflow, person, or use case that a relevant right-side illustration can explain. Use approved assets or create a representative 2D/3D illustration for that side; do not fill it with unrelated abstract decoration. For a task-first or information-dense app, keep the first action visible and reduce or omit hero artwork if it delays that action. If the choice is genuinely uncertain, prototype both with the same copy, CTAs, brand tokens, and viewport sizes, then compare comprehension, visual balance, and mobile behavior before selecting one.
- When a homepage is the requested deliverable, let it read as the product's front door rather than a design-study dashboard. Keep navigation and controls quiet, give the hero generous space, and move detailed workflow cards and comparison controls out of the first impression. Use a supplied visual reference to identify hierarchy, density, and level of polish; do not copy its exact copy, layout, or unsupported claims.
- Make a workflow illustration credible for its domain: show a small number of meaningful stages, real labels and relationships, and an outcome a viewer can trace. Use confirmed sample data or clearly mark illustrative values. Avoid decorative charts, invented performance targets, ambiguous scoring, and miniature UI that becomes illegible at normal viewing size. Review the illustration as carefully as the hero copy at desktop and mobile sizes.
- Give each visual a job before choosing its style or technique: identify what it makes easier to understand about the product, workflow, or next action. A representative scene, product view, or labeled process can carry that explanation. Use background shapes, texture, and light only to support hierarchy and atmosphere; do not let them masquerade as product explanation. Test the still frame first: the key idea must remain understandable without movement.
- For a centered hero, use a background illustration or animation only when it strengthens the message without competing with the text. Choose motion after seeing the final copy and density. For a split hero, animate the right-side illustration only when movement explains a relationship or adds useful emphasis. Plan a meaningful sequence, such as input, transformation, and outcome, or a visible change in product state; keep its labels and outcome readable while paused. If both layouts are offered, implement purposeful motion in each prototype so the comparison reflects the intended experience; also provide stable reduced-motion states. Keep text and CTAs readable over every frame. Autoplaying motion that persists beyond five seconds alongside content needs a pause, stop, or hide control unless essential.
- Judge motion in context: review the first frame, a later frame, the paused state, and the reduced-motion state at desktop and mobile sizes. Check that the illustration does not crowd the headline or CTA, the sequence has a clear beginning and outcome, and the page remains useful if the visual is removed. Revise or omit motion that adds attention without adding understanding.

## Iterate with evidence

1. Name the question for the next pass, such as hero composition, content hierarchy, illustration relevance, or a theme pairing. Keep a usable baseline and preserve promising alternatives.
2. Make the smallest useful change in the image, design, or code. State what must stay fixed, especially logo, palette, copy, and accepted layout decisions. For a new direction, branch from the baseline instead of overwriting it.
3. Review the result with real content at desktop and mobile sizes. Check whether a visitor can understand the headline and supporting line, identify the primary CTA, and act. Check whether the illustration or animation explains anything and whether the design respects brand and accessibility constraints. When comparing both hero layouts, review their animated and reduced-motion states at the same sizes. Use task-based feedback from representative users when available; designer preference alone does not establish usability.
   If the user supplies a homepage screenshot, compare the render against its composition, whitespace, and visual clarity before declaring the iteration ready; preserve the project's own brand and verified content.
4. Turn feedback into a concrete next change or a recorded decision. Distinguish observed problems, stakeholder preferences, and untested assumptions. Continue the cycle; a code render may send the work back to image exploration or layout design. Show a reviewable version when subjective direction needs the user's or design owner's input, and never infer approval from silence.

## Make the concept reviewable

- Translate the selected direction into semantic, responsive HTML and CSS with real text and working interactions. Include the homepage hero and its actual CTA destinations in the reviewable prototype. If two hero directions remain under review, keep both accessible as separate variants with their animations and reduced-motion states. Recreate the layout with elements and reusable tokens; do not use a full-page generated image as the interface. Preserve approved logo files and palette values.
- When multiple approved themes exist, add a usable theme switcher at the lower right of the review prototype. Switching must visibly update the page through shared theme tokens, preserve contrast, work by keyboard, and remain usable on small screens. Do not invent unapproved brand colors to fill missing theme values.
- Check each theme's actual pairings against [WCAG 2.2 text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) and [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html): 4.5:1 for normal text, 3:1 for large text, and 3:1 for meaningful control indicators. If an approved swatch pairing fails, choose another approved pairing or permitted support color; do not alter the swatch value.
- Show the concept image beside or linked from the prototype when useful, and explain intentional differences between the image and implementation. Render and inspect every approved theme at relevant desktop and mobile sizes, including content legibility, logo fidelity, keyboard theme switching, and reduced-motion behavior. Compare new renders with the accepted baseline in a consistent browser environment; inspect meaningful differences rather than accepting a screenshot diff alone. For a live page, use `playwright-verification`; for an implementation handoff, use `design-handoff`.

## Hand off

When the direction satisfies the brief and the user or design owner accepts it, provide the page map, approved asset and token sources, reference links with what each contributed, chosen visual direction, prototype location, accepted decisions, and remaining implementation questions. If feedback is still pending, preserve the current baseline and next question so the following session resumes the loop. Keep client-specific decisions in the project handoff, not in this reusable skill.
