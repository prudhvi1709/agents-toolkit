# Reference selection for application screens

Use this when the task is an application screen or when selecting from a
collection of references. These are starting patterns, not mandatory layouts.
The project's accepted design system and actual task take precedence.

## Select the smallest useful reference

Match purpose, user role, information density, and state. Choose a screen or
component that solves the relevant problem; do not copy an entire product.
Keep brand invariants fixed while exploring layout. If there is no suitable
reviewed example, record the gap and use a provisional pattern rather than
mislabeling inspiration as approved.

| Purpose | Useful pattern | Selection check |
| --- | --- | --- |
| Discovery or request entry | Scope headline, prioritized search/request action, supporting pathways | Does the user need orientation, or are they already working? Keep promotion out of an operational queue. |
| Structured form | Related field groups, explicit required/optional inputs, validation and progress when useful | Does task length justify steps or a context pane? Preserve input after validation errors. |
| Analytical dashboard | Filters, visible active selections, defined KPI summaries, primary and supporting breakdowns | Are definitions, units, denominators and filter effects known? Avoid decorative metrics and unsupported summaries. |
| Work queue | Search/filter, row status, relevant sort, item detail and next action | Does the role need bulk actions, prioritization, or a detail pane? Check empty results separately from no access. |
| Administration | List/detail, role or permission controls, action feedback | Can users identify the affected entity and scope? Do not present analysis controls as account permissions. |
| Document workflow | Required/optional sources, stage feedback, results and retrieval | Is the task actually sequential? Do not force re-upload when the source is already available. |
| Intranet or resource hub | Search/navigation, useful links, secondary news/resources | Is content discovery the task? Avoid importing promotional layouts into transaction screens. |

## Preserve reference provenance

Use the project's handoff or source record, not a global client catalog. For
each selected reference, keep:

- source file/page/frame and version/date;
- purpose, audience/role and state;
- review status and supporting decision, or `unknown`;
- reusable structure and conditions against using it;
- authoritative token source, separate from observed example values;
- consequential correction, reason and resolution when feedback exists.

Record rejected patterns with the reason when it affects later selection.
Do not infer approval from recency, source labels, silence, or generated claims.
Preserve useful structure without importing another product's branding,
performance copy, business metrics or domain assumptions.

## Compare a proposed improvement

When evaluating whether references or extra checks improve output, hold the
brief, content, tokens, agent settings, generation budget and viewports fixed.
Compare the current workflow, added references, added checks, and both together
when that distinction matters. Keep the evaluation target out of the examples.

Record concrete defects and requested corrections by case. Separate observable
failures from preferences, and change presentation order or hide condition
labels during reviewer comparison where practical. Without a reviewer, report
mechanical findings and provisional observations; do not claim acceptance,
reduced rework or a quality gain from a small exploratory comparison.
